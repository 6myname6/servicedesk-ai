## RC-001 移除「等客户」与「重开」，`CLOSED` 拆分为已完成 / 不通过

**变更前**

- 状态 9 个：`NEW` / `ASSIGNED` / `ACCEPTED` / `IN_PROGRESS` / `WAITING_CUSTOMER` / `RESOLVED` / `CLOSED` / `REOPENED` / `CANCELLED`。
- 状态流转 7 个动作：接单、开始处理、等客户、客户回复、解决、验收关闭、重开。
- SLA 带暂停 / 恢复 / 单次 7 天上限（S-02）。
- 终态只有 `CLOSED` 与 `CANCELLED`，验收不通过的出口是「重开」到 `REOPENED`。

**变更后**

- 状态 8 个：`NEW` / `ASSIGNED` / `ACCEPTED` / `IN_PROGRESS` / `RESOLVED` / `CLOSED` / `REJECTED` / `CANCELLED`。
- 状态流转 5 个动作：接单（`ASSIGNED→ACCEPTED`）、开始处理（`ACCEPTED→IN_PROGRESS`）、解决（`IN_PROGRESS→RESOLVED`）、验收通过（`RESOLVED→CLOSED`）、验收不通过（`RESOLVED→REJECTED`）。
- 终态 3 个：`CLOSED`（已完成）、`REJECTED`（不通过）、`CANCELLED`（已取消）。
- 派单可派状态只剩 `NEW`；取消可取消状态为 `NEW` / `ASSIGNED` / `ACCEPTED` / `IN_PROGRESS`。
- SLA 只保留倒计时与超时升级，暂停机制整体移除。

**决策原因**

1. 「等客户」本质是用状态机表达「在跟客户说话」，与 RC-002 的私信职责重叠；客户补充信息不该打断工单状态。
2. 「重开」与「验收不通过」表达的是同一件事，保留两套会让统计口径分裂（重开次数、不通过次数各算一遍）。
3. 验收不通过是需要留档的结论，用状态承载比用「重开 + 备注」可追溯。

**已定的细节**

| 项 | 决策 |
| --- | --- |
| 旧枚举值 | **直接删除**，不保留不可达状态 |
| `paused_at` / `paused_total_minutes` | **保留列不删**，代码不再写入，恒为 `NULL` / `0` |
| `REJECTED` 是否写 `closed_at` | **不写**。`closed_at` 语义是「验收通过时刻」，不通过时间以 `REJECT` 事件为准 |
| 不通过后如何继续处理 | 只能**新建工单**，描述中引用原单号；不提供返工流转 |
| 评价资格 | 仅 `CLOSED` 可评价，`REJECTED` 与 `CANCELLED` 不可 |

**影响面**

| --- | --- |
| 文档 | 开发文档 3.1 / 3.2 / 4.1 / 5.3 / 5.4 / 6.2 / 7.1 / 7.2 / 7.4 / 7.11.1 / 7.11.2 / 7.12 / 7.13 / 7.14 / 7.15 / 11 / 12.1；ER 图 4.5 / 4.6 / 第 6 节；接口文档 枚举表 / 2.6 / 3.1 / A.9 |

## RC-002 新增工单私信（报修人 ↔ 被派工程师）

**变更前**

无对话能力。工程师需要客户照片或补充信息时，只能用「等客户」把工单挂起，再等客户回复后「客户回复」拉回处理中。

**变更后**

- 新增表 `ticket_message`：`id` / `ticket_id` / `sender_id` / `content` / `created_at`，一单一会话。
- 新增接口：`POST /api/tickets/{id}/messages`（发送）、`GET /api/tickets/{id}/messages`（倒序分页查询）。
- 权限：仅本单报修人与被派工程师可发言；主管、管理员只读；三个终态后**所有人只读**。
- 私信**不写 `ticket_event`**，不进时间线；聊天窗独立打开（前端弹窗 / 抽屉）。
- 分页：`page` 默认 1，`size` 默认 20、最大 100，按 `created_at` 倒序；前端翻转后正序展示。
- 实时性：不做服务端推送，窗口打开期间 15 秒轮询一次。
- 本期不做未读计数与已读回执。

**后续**：主管 / 管理员只读的口径已由 [RC-005](#rc-005-私信收窄为仅对话双方可见) 收窄为不可读，非对话双方统一 404。

**决策原因**

1. 沟通是高频行为，占用工单状态会让状态机承担本不属于它的职责，也使 SLA 口径变复杂。
2. 独立成表而不是复用事件表：时间线是工单履历，逐条对话混进去后状态流水难以阅读。
3. 只开给报修人与处理工程师：主管与管理员看得到全局，但参与对话会模糊责任边界。

**影响面**

| 层 | 内容 |
| --- | --- |
| 文档 | 开发文档 3.1 / 3.2 / 5.3（新增 F-06）/ 6.2 / 7.4 / 7.23；ER 图 3.1 / 3.2 / 4.15 / 第 5 节 / 第 6 节 / 第 7 节；接口文档 3.5 / 3.6 / A.21 |
| 表 | 新增 `ticket_message` + `idx_ticket_created(ticket_id, created_at)` |
| 接口 | 新增 3.5、3.6 两条 |
| 代码 | 新增 `TicketMessage` 实体、`TicketMessageMapper`、`TicketMessageRequest`、`TicketMessageVO`、`TicketMessageQueryRequest`、`TicketMessageService` / `Impl`、Controller 两个端点 |
| 测试 | 新增 `TicketMessageControllerTest`：双方发言、主管只读 403、终态 409、未派单 409、超长 400、倒序分页 |
| 前端 | 详情页「私信」入口 + 聊天窗（轮询、向上加载） |

## RC-003 所有写操作绑定工单事件

**变更前**

| 操作 | 是否写事件 |
| --- | --- |
| 建单、派单、接单、开始处理、解决、验收关闭、取消、处理记录 | 已写 |
| 编辑工单 | 不写 |
| 评价 | 不写（只落 `ticket_feedback`） |
| 附件上传 / 删除 | 不写（`ATTACH` 类型已定义但未落地） |

**变更后**

- 新增事件类型 `UPDATE`（编辑）与 `FEEDBACK`（评价）。
- 编辑写 `UPDATE`，`metadata.fields` 记录被改字段名；旧值不入事件。
- 评价写 `FEEDBACK`，`metadata.score` 记录分数；评价正文仍只存 `ticket_feedback`，不双写。
- 附件写 `ATTACH`，`metadata` 记 `action`（upload / delete）、`attachmentId`、`fileName`；在附件与工单关联时写，上传但未关联工单的不写。

**边界**

只记录**写操作**。查看详情、列表、导出、统计等读操作不写事件（只进应用日志），否则事件表会被浏览行为淹没，时间线也失去阅读价值。

**影响面**

| 层 | 内容 |
| --- | --- |
| 文档 | 开发文档 7.15 事件覆盖清单、12.1 字典；ER 图 4.6 的 `type`；接口文档枚举表 |
| 表 | 无 DDL 变更（`ticket_event.type` 是 `VARCHAR(24)`） |
| 代码 | `TicketEventType`（+`UPDATE`、+`FEEDBACK`）、`TicketServiceImpl.update` / `feedback`、`FileAttachmentServiceImpl` |
| 测试 | `TicketUpdateControllerTest`、`TicketFeedbackControllerTest`、`FileControllerTest` 各补一条事件断言 |

## RC-004 时间线改为不分页

**变更前**

`GET /api/tickets/{id}/events?page=1&size=20`，返回 `PageResult`（`total` + `records`），默认 20 条、最大 100。

**变更后**

- `GET /api/tickets/{id}/events` 无参数，直接返回事件数组 `object[]`。
- 排序不变：`created_at` 正序，同一时刻按 `id` 正序。
- 服务端硬上限 500 条，超出时只返回最近 500 条。

**决策原因**

时间线是详情页的固定区块，用户需要一眼看完整个工单履历；分页会把「最新进展」藏在最后一页。单工单事件量为百级，一次返回可接受。

**影响面**

| 层 | 内容 |
| --- | --- |
| 文档 | 接口文档 3.4（请求参数、响应结构、样例）；开发文档 7.15（删分页行，改硬上限）、6.2（P-04 描述） |
| 接口 | 响应从 `PageResult` 变为数组，属于**破坏性变更**（前端需同步改） |
| 代码 | 删 `TicketEventQueryRequest`；`TicketCommentServiceImpl.pageEvents` 改 `listEvents`；`TicketController.pageEvents` 改返回 `List`；`TicketAssembler.assembleEventPage` 改批量组装 |
| 测试 | `TicketCommentControllerTest` 改断言；删除分页上限用例，补 500 上限用例 |
| 前端 | 时间线去掉分页控件，改为列表全量渲染 |

## RC-005 私信收窄为仅对话双方可见

**变更前**

- RC-002：仅本单报修人与被派工程师可发言；主管、管理员只读；三个终态后所有人只读。
- 接口文档 3.5 / 3.6：主管、管理员以「只读」形态存在，发言返回 403。

**变更后**

- 私信只对**本单报修人**与**被派工程师**开放，主管、管理员及其他任何角色都不可读写。
- 非对话双方访问 `POST /api/tickets/{id}/messages` 或 `GET /api/tickets/{id}/messages` 统一返回 **404**，与「消息不存在」不区分，避免通过状态码确认私信是否存在。
- 三个终态后，对话双方只读历史；主管、管理员仍然 404。
- 前端详情页的「私信」入口只对双方展示，主管、管理员不显示。

**决策原因**

1. 私信是双方沟通，不是工单履历；工单全局可见不等于私信可读。
2. 主管、管理员只读会把第三方拉进责任链，出问题时分不清是双方约定还是旁观者判断。
3. 与「越权与不存在统一 404」的全局口径一致，避免用 403 / 404 差异探测私信。

**影响面**

| 层 | 内容 |
| --- | --- |
| 文档 | 开发文档 3.3 / 3.4 / 5.3（F-06）/ 6.2 / 7.4 / 7.23；接口文档 3.5 / 3.6 |
| 表 | 无 DDL 变更 |
| 接口 | 3.5 / 3.6 的权限从「主管、管理员只读 / 403」改为「非双方统一 404」，入参与响应结构不变 |
| 代码 | RC-002 尚未实现；实现时 `TicketMessageService` 的参与方校验放在最前，非双方直接 404，再判状态 409 |
| 测试 | 新增 `TicketMessageControllerTest` 时覆盖：主管 GET / POST 404、管理员 GET / POST 404、双方正常、终态双方只读 |
| 前端 | 详情页「私信」入口仅双方可见 |

## 2. 评审决策记录（2026-11-23）

本次变更由 4 项需求调整触发（RC-005 为后续追加），逐条确认结果：

| # | 议题 | 决策 |
| --- | --- | --- |
| 1 | `WAITING_CUSTOMER` / `REOPENED` 是删值还是保留不可达？ | 删值，直接没有这两个状态 |
| 2 | `paused_at` / `paused_total_minutes` 删列还是留死列？ | 留列不删 |
| 3 | 移除重开后，验收不通过怎么办？ | `CLOSED` 拆成「已完成」和「不通过」，终态三个：不通过、已完成、已取消 |
| 4 | 私信是并入时间线还是独立？ | 私信即私信，新开聊天窗 |
| 5 | 主管 / 管理员能否在私信里发言？ | 不能，只读 |
| 6 | 终态后私信如何处理？ | 聊天关闭，只读历史记录 |
| 7 | 「查看详情」是否需要留痕？ | 不需要 |

> RC-005 已把第 5 条由「只读」收紧为「不可读，统一 404」；第 6 条「只读历史」仅适用于对话双方。

在此基础上由开发侧补充的技术判断（已写入三份文档，如有异议可单独立项调整）：

| # | 判断 | 理由 |
| --- | --- | --- |
| 1 | 不通过的状态名用 `REJECTED`，事件类型 `REJECT` | 与 `CLOSED` / `CANCELLED` 命名风格一致 |
| 2 | `REJECTED` 不写 `closed_at` | 避免污染「关闭时长」统计 |
| 3 | 私信使用独立表，不写 `ticket_event` | 对话不等于工单履历 |
| 4 | 私信保留分页（20 / 最大 100） | 聊天是持续增长的长列表，与时间线诉求不同 |
| 5 | 时间线硬上限 500 条 | 不分页必须有兜底 |
| 6 | `TicketEventVO` 新增 `operatorRole` | 开发文档 7.15 要求事件带操作人角色，前端原型已在使用 |
| 7 | `SlaStatusVO.paused` 保留但恒为 `false` | 与「留列不删」保持一致，前端暂不改 |
| 8 | 新增需求编号 `F-06` | 5.3 需求表中 F-05 之后第一个空号 |
